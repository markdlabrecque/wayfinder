# Workplan: Replace rigid development-workflow choreography with audited contextual policy

> System of record: **Filesystem**

## Objective

Refactor the user-scoped `~/.pi/agent/extensions/development-workflow` extension into a hybrid policy engine: retain deterministic enforcement for safety, authorization, ownership, state integrity, and green merge evidence, while turning sequencing preferences into contextual defaults with explicit, persisted, auditable overrides. The workflow should enforce required artifacts and outcomes rather than one fixed role choreography; support new, adopted-existing, and recovery paths; treat the review limit as an escalation boundary rather than an automatic dead end; and improve worktree/session recovery and diagnostics. Update the user-level Pi/Claude policy parity contract as part of the same change. Before implementation, ratify an executable-evidence contract and architecture contract because these acceptance criteria depend on mechanical coupling.

## Action Plan

1. [ ] Write a policy classification matrix covering every current guard in `index.ts`, `workflow-state.ts`, role prompts, `README.md`, `~/.pi/agent/AGENTS.md`, and `~/.claude/CLAUDE.md`: classify each as non-overridable safety/integrity, overridable outcome requirement, or advisory choreography; explicitly retain production safety, repository trust, unrelated-dirt protection, child authority, file ownership/locking, remote-write approval, reviewer read-only behavior, durable state integrity, and required green release evidence as hard invariants.
2. [ ] Define and approve the architecture contract before coding: the extension owns deterministic authorization, persistence, artifact validation, and audit logging; the foreground Orchestrator owns contextual sequencing and risk decisions; every soft-rule deviation is represented as structured state rather than hidden in prompts; prompts may recommend paths but cannot grant authority or bypass hard invariants.
3. [ ] Define executable acceptance evidence before coding: add an integration matrix that exercises new work, adopted existing work, infrastructure recovery, review-cap escalation, authorized override, denied hard-invariant override, worktree-local plan ingestion, and final reporting; require each scenario to assert persisted state, diagnostics, allowed next actions, and non-regression of child/file/remote safety boundaries.
4. [ ] Design workflow state version 5 with lazy migration from versions 1-4. Add an explicit workflow entry mode such as `new`, `adopt_existing`, or `recovery`; structured deviation/override records containing rule code, reason, decision, risk, actor, timestamp, and supporting evidence; review-escalation state that is recoverable; and logical-role/session-attempt metadata that distinguishes a stable Implementer role from replaceable physical subagent sessions.
5. [ ] Replace the single fixed stage-sequence assumption with outcome-based transition guards. New work should still default to red-first TDD, while adopted work may supply validated historical red/green provenance or a recorded reason for missing evidence. Recovery workflows should resume from durable artifacts without replaying already-satisfied stages. Invalid transitions that threaten hard invariants must remain blocked.
6. [ ] Add a foreground-only `override` or `resolveEscalation` workflow action with a closed enum of overridable rule codes and required structured justification. Reject attempts to override safety, authorization, ownership, repository-integrity, reviewer-read-only, or red-release gates. Persist every accepted and rejected override in diagnostics and include accepted deviations in the Reporter/system-of-record output.
7. [ ] Change review-limit behavior so the configured round count caps automatic Reviewer loops, not all progress. At the cap, persist an escalation and return control to the Orchestrator with explicit choices: narrow Implementer fix plus targeted verification without another review, convert a non-critical item to follow-up, allocate an additional Reviewer round with justification, request user risk acceptance, rescope, or abort. A critical finding must never silently become approved.
8. [ ] Make review routing atomic and unambiguous: `routeReview` should accept and persist the Reviewer’s independent gate evidence and findings in one operation; separately recorded review gates may be referenced by evidence ID without duplicate insertion. Add idempotency keys so retries cannot duplicate tests, findings, cycles, or diagnostics.
9. [ ] Support dedicated worktrees directly at workflow start. Add an explicit target repository/worktree parameter or derive it safely from the approved plan/branch context, run preflight in that canonical root, and resolve `planPath` there. Continue rejecting plans that escape the selected repository, but remove the requirement to copy a valid plan into the foreground session’s unrelated primary worktree.
10. [ ] Add an `adopt_existing` start path that inventories the existing branch, commits, tests, plan/report artifacts, issue ownership, and prior evidence. Require the Orchestrator to explicitly accept each inherited artifact’s provenance; dispatch only the missing roles or gates instead of forcing a synthetic replay of the full pipeline.
11. [ ] Harden subagent recovery: represent stable logical role ownership separately from session attempt IDs; permit a foreground-recorded infrastructure-failure replacement after WebSocket, process, stale-context, or compaction failure; preserve the compact artifact bundle and file claims; ensure transport failures do not consume review cycles or masquerade as implementation failures; and prevent replacement from weakening role authority.
12. [ ] Improve diagnostics and observability. Emit normalized failure events with transport/process/tool reason, role, attempt ID, exit status, duration, and usage; identify which role authored each evidence record; make status counters derivable from diagnostic events; record rejected workflow actions; and add consistency tests ensuring persisted test/review counts match diagnostic summaries.
13. [ ] Refactor role prompts and the compact artifact bundle around responsibilities and required outcomes rather than exact choreography. Keep Test Writer, Implementer, Reviewer, and Reporter authority boundaries, but describe default sequencing as guidance. Require the Orchestrator to name the selected workflow mode, deviations, remaining risks, and next admissible actions in each handoff.
14. [ ] Update `README.md`, `~/.pi/agent/AGENTS.md`, and the corresponding `~/.claude/CLAUDE.md` policy so they describe the same constitutional-core/contextual-shell model. Update `workflow-alignment.test.mjs` to assert semantic parity while translating platform-specific capabilities rather than requiring obsolete hard-coded choreography phrases.
15. [ ] Write red tests before implementation for state-v5 migration, policy classification, hard-invariant denial, audited soft override, adopted-existing evidence, worktree-local plans, atomic/idempotent review routing, review-cap escalation choices, infrastructure session replacement, diagnostic failure reasons, and Reporter inclusion of deviations and unresolved risks. Retain all existing authorization, state-locking, system-of-record, cleanup, and production-safety tests.
16. [ ] Implement a thin retained tracer bullet first: start an adopted-existing workflow in a separate worktree, accept historical evidence, route one blocking review to fixing, hit the review cap with one narrow remaining blocker, resolve it through a foreground narrow-fix decision, record targeted and full-green evidence, report deviations, and complete without bypassing any hard invariant. Expand the remaining modes and override codes only after this vertical path is green.
17. [ ] Mutation-test the policy boundary: deliberately make one hard invariant overridable and confirm tests fail; remove required override justification and confirm audit tests fail; reintroduce duplicate review routing and confirm idempotency tests fail; suppress a transport failure reason and confirm diagnostics tests fail; then restore each mutation before final gates.
18. [ ] Run the complete extension and subagent test matrix from the extension README, including `workflow-alignment.test.mjs`, policy-boundary tests, state migration, integration scenarios in temporary Git repositories/worktrees, model-list smoke checks, and reload/resume smoke tests. Verify existing active version-4 workflows remain readable and recoverable without hand-editing state.
19. [ ] Publish a report comparing before/after behavior using issue #56 as a replay fixture: document eliminated retries and dead ends, preserved hard safeguards, any accepted deviations, test commands/results, migration/rollback procedure, and measured dispatch/time/token improvements. Roll out behind a configuration flag or staged default, observe diagnostics for several workflows, then remove the compatibility flag only after the contextual paths prove stable.
