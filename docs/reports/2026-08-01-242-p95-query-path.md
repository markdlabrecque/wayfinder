# #242 — p95 query-latency scaling fix (bounded collector + composed fq)

Issue: [#242]. Branch: `242-p95-query-path`. Done in the main thread at the
user's direction (no subagent pipeline).

## Problem

At 2M docs the benchmark query's p95 was 93.04 ms vs Solr's 10.42 ms. Two
defects in the query path, both O(total matches) per request regardless of
`rows`:

1. `AllScoredHits` collected **every** match into a `Vec`, materialised sort
   keys for each, and sorted the whole thing — to serve `rows=10`.
2. Each `fq` ran as a separate `DocSetCollector` full pass, then
   `hits.retain(...)` — the filter never reduced the scored set, it only
   discarded work already done.

## Attribution (500k docs, `q=rocket` matching 125,204; N=100/variant)

The ticket suspected fq first; measurement inverted that. Numbers are p50/p95
before the fix:

| Variant | p50 | p95 |
|---|---|---|
| full (fq+facet+hl) | 18.13 | 18.75 |
| no hl | 18.05 | — |
| no facet | 16.35 | — |
| no fq | 15.15 | — |
| bare q only | 11.93 | — |
| bare q + fq | 16.37 | — |
| match-all `*:*` rows=10 | 15.77 | — |

The unbounded collector dominated (~12 ms to collect+sort 125k matches); the
fq retain added ~4.4 ms; facet ~1.8 ms; hl ~0.1 ms.

## Fix

- **`TopScoredHits`** (`src/collector.rs`): bounded counterpart of
  `AllScoredHits`. Per segment it keeps at most ~`2 * limit` candidates —
  when the buffer fills, `select_nth_unstable_by(limit - 1)` + truncate, then
  a threshold skip against the current `limit`-th best. Every match is still
  counted and folded into a global max score, so `numFound` and `maxScore`
  keep their exact semantics. Correctness: the global top-`limit` is a subset
  of the union of per-segment top-`limit`s, and the shared comparator's
  `DocAddress` tie-break makes the order total and deterministic.
- **Shared comparator**: the ordering was extracted into a free function
  `compare_hits` used by both collectors, so the bounded path cannot drift
  from the fixture-pinned order (`select_all.json`,
  `select_sort_score_all.json`). `TopDocs::order_by_fast_field` could not be
  used — no composed `score desc,id asc`, no asc-score, no multiValued
  min/max selector.
- **`search_top`** (`src/core_index.rs`): composes fqs into the main query as
  scoreless `Must` clauses (`ConstScoreQuery` of `0.0`), so intersection
  happens inside Tantivy's posting-list iterators. Scores are bit-identical
  (`s + 0.0 == s`).
- **`/select`** (`src/lib.rs`) now calls `search_top` with
  `limit = start.saturating_add(rows)`; no preallocation of `limit`, since
  `start` is client-controlled and unbounded. `rows=0` short-circuits to
  count-only. MLT stays on the unbounded `search()` — it indexes the full hit
  list by match offset.

## Evidence

- Tests written red-first (`E0432` on the new API), two new tests in
  `src/core_index.rs`: bounded-vs-unbounded prefix equality across three sort
  shapes and five limits over a two-segment corpus with score ties; fq
  narrowing with independently computed expectations.
- Full suite green: 931 tests / 50 suites; `cargo fmt --check` and
  `cargo clippy --all-targets -- -D warnings` clean.
- Mutation-tested: flipped threshold direction, dropped match counting,
  off-by-one merge truncation, fq const score `1.0` — all four caught, all
  reverted.
- **500k after the fix**: full-query p95 **18.75 → 4.03 ms** (p50 3.58).
  fq now *speeds up* the query (narrower iterator) instead of costing 4 ms.

## 2M benchmark (`bench/run.sh 42 2000000`)

| Metric | Before | After | Solr |
|---|---|---|---|
| p95 query latency (facet+fq+hl) | 93.04 ms | **13.97 ms** | 9.78 ms |
| RSS growth under query load | +705.9 MB | **+7.8 MB** | — |

6.7x faster; the per-request allocation (full match set + DocSet per fq) is
gone, which is where the 700 MB of query-load RSS growth went. Wayfinder is
still ~1.4x Solr's p95 at 2M docs — the remaining gap is not the collector
(bounded now) and was not attributed in this pass. The `<= baseline` PRD
target is close but still missed; recorded in `docs/benchmarks.md` as real
numbers.
