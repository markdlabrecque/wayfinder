# Report: bench corpus-size mislabeling (issue #63)

- Branch: `63-bench-corpus-labeling`
- Scope: fix two real bugs in `bench/src/results.rs`'s markdown-table
  renderer, both left over from issue #13's round-2 review.

## What was built

Two bugs in the results table:

1. **p95 latency row's corpus-size label was hardcoded.** The row always
   printed `"p95 query latency (facet+filter+highlight, 50k docs)"`
   regardless of the run's actual `corpus_size`. Fixed by interpolating
   `results.corpus_size` into the label.
2. **Sub-2M runs silently discarded a real measurement.** The renderer
   computed the real resident-memory-under-query-load number for every
   run, but only ever surfaced it under a `"2M docs"` label gated on
   `corpus_size >= 2_000_000`; anything smaller always rendered "not
   measured" even though a real number existed. Fixed by adding a second,
   honest `"Resident memory, {corpus_size} docs under query load"` row for
   any run whose corpus size is not exactly 2,000,000.

Also reworded `render_report.rs`'s generated intro prose from
`"{corpus_size}-doc corpus"` to `"a corpus of {corpus_size} docs"`, so
non-round corpus sizes (e.g. 50000) read naturally without inconsistent
digit-grouping against the raw-digit labels used elsewhere in the table.

## Round-1 implementor mistake

Round 1 fixed the p95 label interpolation and added the new honest memory
row, but got the gate wrong two ways:

- Used `corpus_size >= 2_000_000` for the new honest row's *suppression*
  condition, which meant any run **larger** than 2M (e.g. 5M) also lost its
  honest memory row — silently discarding the real number for that run,
  which is the exact bug being fixed, just relocated to the other side of
  the threshold instead of eliminated.
- Hand-edited the generated `docs/benchmarks.md` artifact directly instead
  of fixing the actual generator, `bench/src/bin/render_report.rs`. Any
  future regeneration of that file would have silently reverted the fix.

Round-1 review bounced on 4 items (these two, plus two others already
resolved before this report's scope).

## Round-2 fix (commit `8459969`)

- Changed the gate from `>= 2_000_000` to `== 2_000_000`, so the literal
  PRD 2M scenario keeps its dedicated `"2M docs"` row, and *every other*
  corpus size — above or below 2M — gets its own honest
  `"{corpus_size} docs under query load"` row. No case silently discards a
  real measurement anymore.
- Fixed `render_report.rs`'s generator at the root instead of hand-editing
  the generated doc (see prose reword above).
- Reverted the round-1 hand-edit to `docs/benchmarks.md` entirely, leaving
  it untouched. The sub-2M honest memory number needed to regenerate the
  file honestly was never recorded by the old (pre-fix) benchmark run, so
  there was nothing correct to write into it by hand.
- Added/fixed tests in `bench/tests/results_table.rs`: an 8-line
  literal-2M table-shape test, a 9-line sub-2M table-shape test (both
  full-text pinned), and a 5M "above 2M" regression test confirming the
  fixed gate no longer suppresses the honest row for large runs.

Round-2 review: **approved, ready to merge.**

## Trivial fix folded in at report time

`bench/tests/results_table.rs`'s "Interpretation" comment (lines ~118-122)
said the honest row is emitted "only when corpus_size < 2_000_000" — stale
after the round-2 gate change to `== 2_000_000` (equivalently, the honest
row now fires for `!= 2_000_000`, both above and below). Corrected the
comment wording to match (commit `f6a1278`, comment-only, no test/logic
change).

## Follow-ups (not actioned in this PR)

- **`docs/benchmarks.md` still shows the pre-fix output.** The committed
  file was generated by an actual `bench/run.sh 42 50000` run before this
  fix landed, so it still literally contains the old hardcoded
  `"p95 query latency (facet+filter+highlight, 50k docs)"` row (confirmed:
  `docs/benchmarks.md` line 10 as of this report) and no honest
  `"Resident memory, 50000 docs under query load"` row (line 8 still says
  "not measured"). Leaving the generated artifact untouched here was the
  correct call — the sub-2M memory number needed to regenerate it honestly
  was never recorded by the old code, so there was nothing correct to
  hand-write — but it does mean issue #63 closes with the user-visible
  committed doc still displaying the pre-fix output. **Recommend filing a
  follow-up issue to regenerate `docs/benchmarks.md`** via a real
  `bench/run.sh 42 50000` run on a Docker host, so the committed doc
  reflects the fixed renderer.
- **Pre-existing, not introduced by this PR** (noticed during review):
  - `bench/tests/results_table.rs`'s module doc still says "five columns",
    but the table actually has six columns since issue #13's round-2
    review added the Measurement-path column.
  - `bench/README.md` and `bench/run.sh` still describe the harness as
    "the 50k benchmark," even though corpus size is actually a runtime
    parameter, not a fixed 50k.
  - Both are cosmetic and out of scope for #63; noting them as candidates
    for a future doc-cleanup pass.
