# #295 — `{!tag}` on `fq`, `{!ex}` on `facet.field`/`facet.query`

Multi-select faceting, the server-side root cause of three Drupal module
descopes. Branch `295-facet-tag-ex`, wave-1 branch **E** of the
#289–#302 parity batch.

## Spec

Findings 136–140 in `docs/solr-ref-findings.md` (captured against real
`solr:9` on the canonical 5-doc `content` core, #310). The one-sentence version:
`{!tag=name}` on an `fq` labels that filter; `{!ex=name}` on a `facet.field` (or
`facet.query`) counts that facet as if the labelled filters were absent.
Everything else about faceting is unchanged, and **there is no error path** —
every near-miss (empty values, a tag nobody set, a tag on `q`) degrades to the
filtered counts with HTTP 200.

### Invariant relied on

`excluded_base_clauses` treats `base[0]` as the non-excludable main `q` clause
and `base[1..]` as the `fq` clauses aligned 1:1 with `fq_tag_lists(params)`.
This holds because `facet_counts`/`facet_counts_fused` are called only from
`/select`, where `base` is built as `once(q).chain(filter_queries)`; in the
no-`q` (`parsed == None`) case `base` is just `[(Must, EmptyQuery)]`, there is
no trailing `fq` clause to exclude, and the empty result is unaffected.

### Deliberate simplification

A request with any `{!ex=…}` forgoes the #246 fused aggregation for the whole
`facet.field` set. Multi-select facet requests are rare and not the hot path,
so this is the smaller, correct change; `FacetFieldsPlan::exclusion_active`'s
doc comment names the ceiling.
