# Report: BM25 static-string ranking (issue #47)

## Approved spec / acceptance criteria

- `q=category:animals` must return `doc1`, then `doc4`, matching Solr.
- A fixture-derived regression test must fail if field norms return on `string`/`keyword`.
- Do not duplicate or broaden scoring work if `main` already has the root-cause fix.
- Run fmt, clippy, and tests.
- PR/report must distinguish required ranking-order compatibility from PRD ratified divergence 4, which permits only BM25 score-magnitude differences.

## Completed behavior and provenance

Issue #47 was already fixed incidentally by merged PR #49:

- Merge commit: `c1a0bc273497f1540c961bb141b26288fbc267ee`
- Fix commit: `19397587ba9b9fcec195dae286568be41dd45438`
  (`fix(schema): unanalyzed string/keyword fields carry no fieldnorms`)

The root cause was Tantivy field norms on the multi-valued static `category` string field. Norm-based BM25 length scoring favored `doc4` (one category value) over `doc1` (two values), producing the incorrect `doc4, doc1` order.

Current static `string` and `keyword` fields both resolve through `ResolvedType::Str` in `src/schema.rs:523-544`. They use the raw tokenizer, `Basic` index records, and `set_fieldnorms(false)`; stored and fast options remain conditional, with fast strings using the raw tokenizer. This matches Solr `StrField`'s `omitNorms=true` behavior for this case.

Fixture and regression coverage already existed:

- Fixture: `solr-ref/responses/select_q_field_term.json`
- Manifest registration: `solr-ref/manifest.tsv:114`
- Capture registration: `solr-ref/capture.sh:1327`
- Regression test: `tests/query_types.rs:673-684`,
  `select_q_field_term_string_field_has_no_length_norm`

The fixture and test require `doc1, doc4` for `q=category:animals`.

## Deferred follow-up

One non-blocking concern remains, outside issue #47:

- **Dynamic JSON catch-all field norms** at `src/schema.rs:586-600`: the `_dynamic` JSON catch-all's `TextFieldIndexing::default()` does not explicitly disable field norms. Dynamic string/keyword queries may therefore be length-normalized differently from Solr `StrField`.
- This was not exercised by #47's static-field fixture and is not fixed or verified here. Do not claim dynamic string scoring is fixed.
- Any change requires its own rank-discriminating Solr fixture and regression test for a multi-valued dynamic string field before implementation.
