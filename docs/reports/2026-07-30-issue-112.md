# Issue #112 — `q=*:*` edismax queries ignored an invalid `qf` entirely

**Branch:** `112-edismax-qf-star`
**Status:** implemented, reviewed, follow-ups actioned by reporter, ready to merge.

## What was built

Real Solr 400s on an invalid `qf` field name under `defType=edismax` even when `q=*:*`
(finding 84, issue #111 fixed this for non-`*:*` queries; the `*:*` case was missed). Wayfinder's
`parse_edismax_query` (`src/core_index.rs`) had a `q.trim() == "*:*"` short-circuit that returned
`AllQuery` *before* the `qf`-validation loop added for #111 ever ran, so `q=*:*&qf=nosuchfield`
silently 200d with all docs instead of 400ing.

**Fix:** moved the existing `field_target`-based `qf`-validation loop (originally added for
#111, around what is now lines ~990-1028 of `src/core_index.rs`) to run *before* the `*:*`
short-circuit. The short-circuit itself, and the subsequent
`resolve_field_weights(...).is_empty()` / `default_field` lookups, are unchanged and still run
after it — deliberately, since a valid (or absent) `qf` is irrelevant once every doc matches.

## Test coverage

`tests/edismax.rs`:
- `star_query_with_undefined_qf_field_still_400s` — `q=*:*&qf=nosuchfield` must 400.
- `star_query_with_partially_invalid_qf_still_400s` — `q=*:*&qf=title+nosuchfield` must 400 on
  the undefined name alone, even though `title` is valid.

Both assert only the narrow envelope contract already established by `tests/error_shapes.rs`
(status code, `error.code`, non-empty `error.msg`, and `error.metadata` key shape) — never
Solr's Java exception text verbatim.

Fixtures (captured against real Solr, one-off container, not re-run through `capture.sh`, same
schema as the #111 capture):
- `solr-ref/responses/edismax_qf_star_unknown.json` (`qf=nosuchfield` alone)
- `solr-ref/responses/edismax_qf_star_partial_invalid.json` (`qf=title+nosuchfield`)

Both were **untracked** going into the reporter stage; committed as part of this change.

Existing coverage confirmed unaffected: `star_colon_star_matches_everything_under_edismax`
(`tests/edismax.rs:189`) already covers `q=*:*` with a *valid* `qf` and still passes, so the
positive path is not regressed by the reorder.

`docs/solr-ref-findings.md` finding 85 records the underlying Solr fact and the fix; the
`capture.sh` comment block documenting the two captures (not `cape` calls — same non-verbatim
error-envelope reasoning as #111's block) was moved by the reporter to the end of the file per
repo convention (see Follow-ups below).

  -- -D warnings` clean.
- The "missing positive test" concern raised during review was a false alarm —

passes" caveat for this issue.

## Follow-ups from review, actioned by the reporter

1. **`capture.sh` block placement.** The new comment block (documenting the two #112 captures)
   had been inserted mid-file, adjacent to the #111 block, rather than appended at the end per
   repo convention ("append your block at the end of `capture.sh` so concurrent branches merge
   mechanically"). The reporter cut it and appended it as a new final block
   (`# --- q=*:* with a bad qf (issue #112) ---`).
2. **Finding 85 gap.** `docs/solr-ref-findings.md` had no entry for the #112 fact at review time.
   The reporter added finding 85, in the same style as findings 82-84, cross-referencing finding
   84 and stating explicitly that the fix required moving the existing #111 qf-validation loop
   ahead of the `*:*` short-circuit.
3. **Untracked fixtures.** `solr-ref/responses/edismax_qf_star_unknown.json` and
   `edismax_qf_star_partial_invalid.json` were untracked at review time. The reporter staged and
   committed them alongside the code/test/doc changes.
