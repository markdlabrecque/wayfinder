# Report: `fl=score` — per-doc BM25 score field + `response.maxScore` (issue #34)

- Branch: `34-fl-score`
- Scope: implement `fl=score` so a per-doc `score` key and `response.maxScore`
  render when requested, matching Solr's captured wire shape.

## What was built

- `src/core_index.rs`: `render_doc` gained a `score: Option<Score>` parameter.
  It inserts a `"score"` key into the doc JSON iff `fl` explicitly names
  `score` (a `Some(score)` passed without `fl` requesting it stays omitted),
  positioned after the schema-declared stored fields and before dynamic
  fields. That position is flagged in-code as a `ponytail:` unverified
  assumption: no captured fixture has a dynamic field alongside `fl=score`,
  so score-before-dynamic-fields is untested against score-appended-last, and
  finding 24 in `docs/solr-ref-findings.md` (Solr appending its own
  pseudo-fields like `_version_`/`_root_` at the end in `select_all.json`) is
  evidence pointing the other way, since `score` is itself a pseudo-field.
- `src/lib.rs`: threads `(score, addr)` through the paging loop instead of
  discarding the score; builds the `response` envelope via a `serde_json::Map`
  (mirroring the existing `response_header` pattern) so `maxScore` can be
  conditionally inserted between `start` and `numFoundExact` — the key order
  observed in the fixtures (`numFound, start, maxScore, numFoundExact,
  docs`), which a `json!` object literal can't express conditionally.
  `maxScore` is the max score across the full unpaginated hit list, gated on
  `fl` requesting `score` via a single `wants_score` check shared by both the
  per-doc key and the envelope key. Also `ponytail:`-flagged as unfixtured:
  every scored fixture has `start=0` with the whole result set on one page,
  so page-max vs. global-max is untested; zero-hits behavior (key omitted
  rather than emitting `0.0`) is likewise unverified against a real Solr
  capture.

## The BM25-parity finding and resolution

- Discovered mid-implementation: Tantivy's BM25 floats diverge from Solr's
  captured floats by a non-constant ~1.9x-2.3x ratio (e.g. `select_term_scored`'s
  `doc2`: Tantivy ~0.875 vs. Solr's captured 0.457; `select_quick_scored`'s
  `doc3`: Tantivy ~0.940 vs. Solr's captured 0.413) — a genuine
  scoring-formula difference (idf / length-normalization), not a wiring bug.
  The ratio moving per-doc rules out a missing constant factor. Doc *ranking
  order* matches Solr exactly for both fixtures.
- Escalated to the project owner per the issue's own instruction to escalate
  with the diff rather than silently widening the tolerance.
- Owner's decision: exact BM25 float parity is out of scope. Wayfinder's
  compatibility contract (`CLAUDE.md`: "Wire format only... Never Solr's
  config format") is to Solr's wire semantics, not bit-for-bit parity with
  Solr/Lucene's internal ranking math. What matters and is verified: doc
  ranking order, and the `score`/`maxScore` keys' presence, position, and
  type.
- Formalized as **ratified divergence #4** in `docs/PRD.md`'s "Ratified
  divergences from captured Solr behaviour" — permanent and documented, not a
  self-expiring to-do, alongside the existing 3.
- `tests/differential.rs` gained `RANKED_SCORE_VALUE_RATIFIED`, the
  ranked-relevance parallel to the pre-existing `ACCEPTED_DIVERGENCES`
  pattern. It waives only the `response.docs[*].score` *value* for
  `select_term_scored`/`select_quick_scored`; doc ranking order
  (`response.docs[].id`) and `response.maxScore`'s presence/type are still
  hard-checked, and a `score` key missing on either side (vs. a
  present-on-both magnitude mismatch) is explicitly treated as a real
  failure, not silently swallowed by the waiver.

## Test coverage

  the `render_doc` contract directly: `score` present and correctly valued
  when `fl` requests it; `score` omitted when `fl` doesn't, even with a real
  score available.
- `tests/differential.rs`'s hermetic fixture harness

## Follow-ups (explicitly not addressed — for future issues, not implemented here)

- Scores serialize at f64 width (`0.8754687905311584`) vs. Solr's float
  precision (`0.45748958`) — consider emitting the `f32` shortest repr.
- `fl` only splits on `,`; Solr also accepts space-separated (`fl=id score`),
  which now silently drops `score`.
- `fl=*,score` (a common idiom) returns a doc containing only `score` — `fl`
  globs are unsupported in `render_doc` (a pre-existing gap, newly visible
  because of this feature).
- `wants_score` is checked independently in two places (`src/lib.rs` and
  `render_doc`) — two sources of truth for one rule.
- Untested-by-fixture cases worth capturing: zero hits + `fl=id,score`,
  `rows=0`, `start=1` (would discriminate page-max from global-max),
  `sort=<field> asc&fl=id,score`.
