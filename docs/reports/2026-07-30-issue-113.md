# Issue #113 — `edismax` `mm=` (present but empty) must 400, not fall back silently

## What was built

Issue #113's own premise was **wrong**: it claimed real Solr ignores an empty `mm` param
(`mm=`) and falls back to the normal OR default, same as `mm` being entirely absent. A real
one-off Solr capture (same schema/corpus as `tests/edismax.rs`'s other `mm_*` tests) showed the
opposite — `mm=` (present, empty) 400s with `"Invalid 'mm' spec. Expecting an integer."`
(`NumberFormatException`), the same as any other malformed `mm` spec. `mm` entirely *absent* is
unchanged and keeps the normal OR default.

The fix, in `src/core_index.rs` (`CoreIndex::parse_edismax_query`, ~lines 1090–1097):

```rust
if clauses.len() >= 2
    && let Some(spec) = mm
    && spec.trim().is_empty()
{
    return Err(QueryError::Syntax(
        "Invalid 'mm' spec. Expecting an integer.".to_string(),
    ));
}
```

Placement is load-bearing, not incidental:
- **After** the `q=*:*` short-circuit and the empty-`clauses` early return, and **after** `qf`
  validation — a bad `qf` alongside `mm=` must 400 on the `qf` name (matches captured Solr
  precedence).
- **Before** the all-`MustNot`-query `AllQuery` augmentation Wayfinder itself performs — Solr
  never sees that augmented clause count, so checking after it would wrongly inflate a
  single-clause `q=-mission` into a 400 that real Solr answers 200.
- Gated on `clauses.len() >= 2`, because Solr does not validate `mm` eagerly as a request
  param — it only parses the spec when there's a multi-clause boolean query to apply it to.

`src/edismax.rs`'s `min_should_match` lost its `if spec.is_empty() { return clause_count; }`
early return (the pre-fix, silently-wrong-in-the-opposite-direction behavior) — the general path
already returns the same value for an empty spec (`split_whitespace` yields no token, so the
all-required default stands), so the removed line was redundant, not load-bearing.

`docs/solr-ref-findings.md` finding 85 documents the full capture (both halves: the 400 on
multi-clause `q`, the 200 on single-clause `q`, and the `qf`-precedence interaction).

## The two-round review process (worth recording in full — this is a finding about the pipeline itself)

**Round 1:** the implementor placed the guard *before* the `q=*:*` short-circuit, unconditionally
(no clause-count gate). The reviewer bounced this — not because a test failed, but because the
placement rested on an **unevidenced claim about Solr's internal mechanism** (that `mm` is always
eagerly validated). No capture backed that assumption up.

**Round 2:** the implementor did a fresh real-Solr capture specifically to settle the disputed
claim, and it falsified round 1's placement: round 1's guard, if shipped, would have wrongly
400'd `q=*:*&mm=` and `q=-mission&mm=` — both of which real Solr answers 200. The capture showed
Solr only parses `mm` when it has ≥2 clauses to apply it to. The implementor corrected the
placement to the clause-count-gated, post-`qf`-pre-augmentation version above, added the capture
findings to finding 85, and added regression tests (`empty_mm_alongside_a_single_clause_q_does_not_400`,
`empty_mm_400s_for_every_multi_clause_shape_regardless_of_occur`, `whitespace_only_mm_400s_like_an_empty_one`).

**Round 2 reviewer verdict:** APPROVED, no must-fix items. The reviewer explicitly flagged that
the pipeline hit its 2-round cap and recommended a further pass — specifically that the boundary
evidence (which `q`/clause shapes 200 vs 400 under `mm=`) lived only in prose (finding 85, test
comments), not committed fixtures + `manifest.tsv` rows — the identical class of gap that let
round 1's bad placement pass a green suite in the first place (prose evidence is easy to write
around; a differential-harness fixture is not).

## This report's own task: hardening the boundary evidence

Per the reviewer's specific recommendation, and since no live Solr container was available in
this worktree to do a fresh capture:

- Added `solr-ref/responses/edismax_mm_empty_star.json` + a `manifest.tsv` row
  (`edismax_mm_empty_star`) + a `cape` line in `solr-ref/capture.sh`, for
  `q=*:*&defType=edismax&qf=body&mm=&fl=id&wt=json` (a plain 200 GET, legitimately `cape`-able,
  unlike the `mm=` 400 case which stays comment-only per the existing narrow error-envelope
  contract).
- Added a dedicated test, `empty_mm_alongside_star_all_matches_committed_fixture`
  (`tests/edismax.rs`), asserting the response against that fixture via `assert_matches_fixture`.
  It's also swept automatically by the pre-existing generic
  `hermetic_edismax_manifest_entries_match_committed_fixtures` loop, since it's now a real
  manifest row.
- **Important limitation, disclosed rather than hidden:** this fixture's `numFound` (10) is
  corroborated by the implementor's real one-off Solr capture (already cited in
  `empty_mm_alongside_a_single_clause_q_does_not_400`'s comment). Its exact doc-order/id list was
  **not** independently re-captured against a live Solr container for this task — no Docker
  container was running, and I do not have the ability to stand one up in this environment. I
  reconstructed the doc list/order from Wayfinder's own hermetic test run for this exact request
  (verified by adding a temporary probe test, running it, and deleting it — not committed) and
  from the insertion-order convention already established by the genuine real-Solr-captured
  `edismax_mm_absent.json` fixture (a fresh, unmerged, no-sort/no-score index returns docs in
  insertion order in both engines). This is disclosed explicitly in three places: the
  `capture.sh` comment on the new `cape` line, the new test's own comment, and the updated finding
  85 in `docs/solr-ref-findings.md`. **This is corroborating evidence, not yet independently
  verified real-Solr evidence, for anything beyond `numFound`.** Re-running `capture.sh`'s
  edismax block against a live Solr container is the concrete remaining step to close that gap.
- Updated `docs/solr-ref-findings.md` finding 85 with a "Reviewer round-2 follow-up, actioned"
  paragraph naming exactly what was hardened and what remains prose-only.

## Follow-ups explicitly NOT actioned (deferred to a future issue)

Named here rather than silently dropped, per the reviewer's round-2 notes:

1. **`error.msg`/`error.metadata` verbatim comparison on the error path.** The narrow contract
   (`tests/error_shapes.rs`) deliberately does not compare Solr's Java exception text against
   Wayfinder's own — this is by design, not an oversight, but the reviewer noted it as worth
   revisiting if the project ever wants tighter error-message parity.
2. **The three unasserted 200 shapes in `empty_mm_alongside_a_single_clause_q_does_not_400`.**
   `q=alpha` (numFound 3) and `q=-mission` (numFound 8) are still asserted only by `numFound`
   comparison against prose-cited capture numbers, not by committed fixtures — same gap class as
   the `q=*:*` case this report hardened, just not yet done for the other two points on the
   boundary. The three multi-clause 400 shapes in
   `empty_mm_400s_for_every_multi_clause_shape_regardless_of_occur` are likewise status-only,
   uncorroborated by any fixture.

Both of these should go into a follow-up issue that also covers doing a real, fresh
`capture.sh` run (in an environment with Docker available) to replace the reconstructed
`edismax_mm_empty_star.json` doc order with an independently re-verified one, and to add
fixtures for the remaining boundary points named above.
