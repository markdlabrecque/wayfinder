## Headline 1 — the clause-grammar fixtures overturned the issue's premise

The issue's guess was that Solr's comma between sort clauses might be
**optional**, so `sort=id asc category desc` could be two clauses in Solr
and Wayfinder was silently dropping the second. The captured truth is the
opposite: **the comma is mandatory**. `sort=id asc category desc`,
`sort=id asc garbage`, and `sort=id asc category` are all Solr 400s — a
direction error at `pos=2` — because everything from the field token to the
next comma or end of spec must be exactly `asc`/`desc`. Wayfinder had been
answering 200 and silently dropping the extra tokens. So "never a silent
fallback" was violated, but by a different mechanism than the issue
predicted (extra-token-drop, not two-clauses-collapsed-to-one).

Grammar per finding 34: a field is a whitespace-delimited token; a comma
glues onto the following token and fails **field** resolution instead
(`sort=,id asc`, `sort=id asc,,category desc` → a third field-error wording,
class-matched by `tests/sort.rs::sort_error_class`, not verbatim). Direction
is checked before field resolution, trimmed to exactly `asc`/`desc`. Trailing
comma, whitespace around the comma, and an empty `sort=` are all fine (200).

Finding 35: `pos` in the direction error is **absolute** in the whole spec,
not clause-relative (`pos=9` for `sort=id asc,id sideways`, `pos=15` for
`sort=id asc,category`, `pos=4` for leading whitespace) — the one inference
the prior implementation got right, now captured rather than assumed.

## Headline 2 — missing numeric/float/date values sort as 0, not last

Finding 36: a document missing a numeric, float, or date sort value sorts as
the value 0 (epoch for dates) — not first, not last. This is **not** the
missing-last behaviour of string/`SortedSet` columns (finding 16, unchanged
by this issue). `s6`'s negative values are what make missing-as-zero
distinguishable from missing-first at all: the missing doc lands between
`-5` and `10` under `views asc`, not before `-5`. Wayfinder's previous
missing-last-for-everything comparator was a real, captured divergence,
fixed in `src/collector.rs` — the value kind is resolved once in
`check_sort` and carried on `SortClause.value_kind`, consumed by the
per-column missing default in `SegmentSortColumn::value`/`open`.

Finding 37: the Lucene min/max selector (min for `asc`, max for `desc`)
holds for multi-valued numerics exactly as for strings, composed with
missing-as-zero. The corpus deliberately makes `nums desc` **not** the
reverse of `nums asc` (min-order and max-order disagree), which is what
proves a selector is in effect rather than a direction flip.

## Absent-arm finding

`SegmentSortColumn::Absent` is unreachable in practice: Tantivy 0.26's
`FastFieldsWriter::new` calls `record_column_type` for every declared fast
field at writer construction, so every segment carries every declared fast
field's column, and a valueless doc goes through the per-doc missing
defaults in `value()` instead of the `Absent` arm. This was verified by
planting a panic in the `Absent` construction and running the whole sort
suite green (confirmed by the comment at `src/collector.rs:213-214`,
"verified by planting a panic here and running the whole sort suite; issue
#32 review round 2"), and independently confirmed against the Tantivy source
by the round-2 reviewer. I was not able to independently re-locate the
Tantivy 0.26 source in this environment's cargo registry cache to re-verify
the `fastfield/writer.rs:84-90` line reference myself — that citation rests
on the round-2 reviewer's confirmation, not on a re-check by this reporter.
Ruling: keep the `Absent` arm with its zero defaults as defensive code (it
is correct if a future Tantivy version stops materialising empty columns).
Comments were corrected in commit `c7b85b7` to state the arm is defensive/
unreachable rather than describing a live scenario that cannot occur.

## Follow-ups (deferred, not actioned)

1. `pos` in Wayfinder's direction error is a Rust byte offset; Solr's is a
   Java string index — they diverge for non-ASCII field names (e.g.
   `sort=café sideways` would give Wayfinder `pos=5`, Solr presumably `4`).
   Uncaptured. `error.msg` is outside the compatibility contract (finding
   10), so this is a known gap rather than a bug to fix blind.
2. Uncaptured comma corners the reviewer **suspects but has not verified**
   differ in error class: `sort=id,category`, `sort=,`, `sort=id asc,,`.
   Wayfinder currently answers a direction error for these; Solr is
   suspected to answer a field error instead. Needs a `capture.sh` row
   before any code change — do not build to the inference.
3. `sort=%20%20` (a whitespace-only sort value) answers 200 with default
   order, but only the truly-empty `sort=` value is captured
   (`sort_clause_empty`). Cheap capture, not yet done.
4. `sort_clause_space_before_comma`/`sort_clause_space_after_comma` pin
   "200," not "two clauses were actually parsed" — `id` is the corpus's
   unique key, so a second clause can never visibly reorder anything.
   Accepted only because `err_sort_second_clause_*` independently pin that
   the second clause is parsed and checked.
5. `sortdebt_get`/`sortdebt_post_docs` duplicate roughly 80 lines of
   `common::get`/`post_docs` because `common::CORE` is hardcoded to the
   `content` core. A `common::get_core`/`post_docs_to` pair would delete the
   duplication. Out of scope here: `tests/common/*` is frozen for parallel
   work per `CLAUDE.md`.
6. Whether the defensive `Absent` arm should eventually be removed rather
   than kept-and-commented is unresolved; round-2 ruling was to keep it for
   now.
