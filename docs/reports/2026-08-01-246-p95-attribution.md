## Attribution pass (this is the deliverable — measured, not assumed)

2M docs, N=100, 16 distinct single-term queries, benchmark query shape
(`q=<w>&defType=edismax&qf=title body&fq=category:animals&facet=true&facet.field=category&hl=true&hl.fl=body&rows=10`).
Wayfinder native, Solr 9 in Docker, seed-42 corpus. Wayfinder's samples were
tight (min ~= p50); Solr's were noisy through the Docker port-forward.

| Variant | WF before p50 | WF before p95 | Solr p50 | Solr p95 |
|---|---|---|---|---|
| full (fq+facet+hl) | 13.66 | 13.93 | 7.66 | 9.11 |
| no facet | 7.05 | 7.25 | 4.15 | 10.32 |
| no hl | 13.64 | 13.94 | 7.61 | 9.95 |
| bare q + fq, rows=10 | 6.93 | 7.13 | 8.47 | 10.00 |
| rows=0 (count only) | 5.04 | 5.22 | 7.97 | 9.35 |

- **Ticket suspect 1 (Solr query-result caching): the first measurement said
  DISPROVED and was WRONG. See "Correction: suspect 1" below.** No cache was
  built either way, but the reason recorded here originally does not hold.
- **Suspect 2 was the gap.** Faceting cost 6.6 ms (13.66 → 7.05), the largest
  single component; a count-only pass over the same query cost 5.04 ms, so
  ~5 ms of that 6.6 was a *second full iteration* of the same matching set.
- **Suspect 3 (block-max/WAND skipping) was not opened** — it conflicts with
  exact `numFound` and global `maxScore`, and fusing was expected to be
  enough.
- At **500k** Wayfinder was already faster than Solr on every variant (full
  3.76 vs 5.61 p50). The gap was 2M-only.

## Correction: suspect 1 (added after the fix landed, before merge)

The original disproof above is invalid. Its harness (`attribute.sh`) was
re-run repeatedly with `SKIP_INDEX=1` against a **persistent** Solr container,
so by the time the cold/warm block executed, all 16 terms were already in the
queryResultCache from earlier invocations. Both the "cold" and the "warm"
sample were cache hits, which is exactly why they came out equal (7.97 vs
8.24). The test could not have detected a cache effect.

Re-measured with a harness that proves its own cache state, 2M docs, 56
distinct terms, one pass of misses then one pass of hits, paired per term,
**three repetitions**:

| Shape | Solr pass1 (QRC miss) | Solr pass2 (QRC hit) | WF pass1 | WF pass2 |
|---|---|---|---|---|
| plain (`q`+`fq`+`rows=10`), rep2 | 11.84 | 4.10 | 10.24 | 10.21 |
| plain, rep3 | 11.88 | 4.10 | 10.31 | 10.31 |
| full (`+facet+hl`), rep2 | 19.28 | 14.88 | 16.32 | 16.35 |
| full, rep3 | 19.46 | 14.63 | 16.32 | 16.32 |

Paired pass1 − pass2 over three reps: Solr **+4.09 / +5.46 / +5.16 ms**
(plain) and **+4.12 / +3.68 / +3.96 ms** (full). **Wayfinder ran the identical
two passes as a control** — it has no caches, so its delta is pure page-cache
and JIT warmth: **−0.22 / 0.00 / −0.16** and **−0.22 / +0.06 / −0.03**. The
flat control is what makes Solr's delta attributable to the cache rather than
to warmth. Cache counters were byte-identical across all three reps
(`lookups=61 hits=8 inserts=53` on pass 1, `117/64/53` on pass 2).

**So the queryResultCache IS worth ~4 ms, on the faceted shape too.** What
this changes:

- **On uncached queries Wayfinder is ahead** — 16.3 vs 19.4 ms on the full
  shape, 10.2 vs 11.8 plain. Solr's win comes from not executing the search,
  not from executing it faster.
- `bench/run.sh` fires one identical query 200 times, so **Solr's benchmark
  p95 is a fully-cached number and Wayfinder's is not**. The `<= baseline`
  target is being judged against a cached Solr and an uncached Wayfinder, and
  nobody chose that — it fell out of the benchmark's shape. Follow-up issue
  filed to report cold and warm separately and settle which comparison the
  PRD means: **#251**.
- The conclusion "do not build a cache" still stands, but on different
  grounds: not "there is no effect" (there is), but that a result cache is a
  Solr *compatibility* feature — `{!cache=false}`, invalidation on commit,
  mbeans stats — and belongs in its own sized ticket, not in a p95 patch.

Also measured while attributing this, and worth recording so nobody re-runs
it: **the filterCache is not worth building.** Same 56-term paired design,
`fq=category:animals` cacheable vs `{!cache=false}`, with the counters
confirming 49 hits on the cached pass and 0 lookups on the uncached one:
**mean +0.50 ms, median +0.12 ms**.

Three harness bugs had to be removed before any of these numbers meant
anything, all the same class — measuring a cache without checking the cache
counters:

1. Variant order confounded with per-term warmth (the first variant paid the
   cold postings read).
2. S1 and S2 **share a queryResultCache key** — `{!cache=false}` disables the
   filterCache, not the queryResultCache — so whichever ran second was served
   from the other's cached result.
3. `update?commit=true` is a **no-op when nothing changed**, so it opens no
   new searcher and flushes nothing. A core RELOAD is the reliable flush.

The methodological lesson, since it has now cost three bad measurements:
**any cache experiment must assert its own cache counters**, or it is not
measuring what it claims.

## The change

Five commits: `46ad477` (red tests), `09b3a5b` (fusion), `2a82cf9` (must-fix
from review round 1), `398f72f` (drop dead plan field), `e5d1586` (review
round 3 follow-ups). See `git diff 7e854b0..HEAD` for the full diff.

- `CoreIndex::search_top_with_aggs` (`src/core_index.rs`) runs
  `(TopScoredHits, AggregationCollector)` as a tantivy 2-tuple collector in
  ONE pass. `compose_filtered` is shared with `search_top` so the fused
  aggregation provably cannot see a different doc set than the hit list.
- `facet.rs` split into `plan_facet_fields` (pure validate/resolve) and
  `render_facet_fields` (shaping). `facet_fields` was reimplemented on the
  same plan+shape code, so fused and unfused run identical shaping.
- `select` (`src/lib.rs`) plans before the search; on ANY planning error it
  discards the plan and falls through to today's exact `search_top` +
  `facet_counts` path, which is what keeps error semantics bit-identical.
- Out of scope, still their own passes: `facet.query`, `facet.range`,
  `facet.missing`'s `ExistsQuery` count, `stats`.

## Review (2 rounds, approved)

Round 1 BOUNCED with a real must-fix that the reviewer verified in tantivy
0.26.1 source: fusing put all facet fields in one `Aggregations` map sharing
one `AggregationLimitsGuard`, and `AggregationResults::get_bucket_count`
sums across top-level aggs. With `MAX_FACET_TERMS == DEFAULT_BUCKET_LIMIT ==
65000`, any two facet fields whose dictionaries summed past 65000 would fail
where they previously passed — and worse, the failure surfaced as a 500
`wayfinder::SearchError` instead of the 400
`wayfinder::FacetError`-with-`response`-block the unfused path produced.
Fixed both halves: `fused_bucket_limit(n) = MAX_FACET_TERMS * max(n,1)`, and
aggregation-class errors fall back to the unfused path.

Two subtleties worth recording accurately, both discovered by mutation
testing:

1. Sizing the guard to arity doesn't merely restore the old headroom — it
   makes the bucket-limit error **unreachable by construction** for terms
   aggs, because `cut_off_buckets` caps each agg at `size` before the sum is
   checked. So the error-fallback's live job is the shared memory ceiling
   plus defence in depth.
2. The **memory** ceiling was deliberately NOT scaled. The unfused peak was
   `max_i(mem_i)` (sequential passes, guard dropped between); the fused peak
   is `sum_i(mem_i)` (all N segment collectors live at once). So a fused
   request genuinely CAN trip a 500 MB ceiling the unfused one would not —
   that is handled by the fallback rather than by widening a fixed server
   ceiling into a request-controlled one.

Mutation results on the new
`two_facet_fields_over_a_dictionary_larger_than_one_fields_budget` test (33k
docs, one field under two `{!key=}` labels, 66k buckets, 1.5s hermetic):
reverting the guard alone PASSES, reverting the fallback alone PASSES,
reverting both FAILS with a 500 and "bucket limit was exceeded. Limit:
65000, Current: 66000". Explanation: each half alone is masked by the
other, per the two subtleties above. Round-1 mutation testing of the fusion
itself (aggregation reading a doc set without the fqs) was caught by six
tests.

## Unflagged behaviour change to record

`facet_fields` (the unfused path) now validates every field up front before
executing any pass, where validation and execution previously interleaved
per field. Diverges only when an earlier field's *execution* errors while a
later field fails *validation* — the message swaps. Both are 400
`wayfinder::FacetError` with the `response` block; status, error code and
envelope unchanged, message only.
