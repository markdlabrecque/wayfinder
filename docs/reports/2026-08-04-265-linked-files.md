## What shipped

The gap that motivated porting `search_api_attachments` into
`search_api_wayfinder` at all: a link to a downloadable document can appear
anywhere in a node — body text, a link field, a paragraph, a Layout Builder
block — and its extracted text is now indexed as part of that node.
`FileExtraction` (#262) handles files in file/image fields; this slice handles
files the content only references by link or embed. `search_api_attachments`
itself never did this; its `search_api_attachments_bf` side-module only matches
absolute URLs whose host equals the site's, has no stable release, and was last
updated in 2019.

- **`LinkedFileDiscovererInterface` + `LinkedFileDiscoverer`** (`src/`): the
  pure discovery logic, behind an interface so it is unit-testable per
  mechanism in isolation from the Search API processor. Four mechanisms, in the
  issue's reliability order:
  1. `data-entity-type` / `data-entity-uuid` attributes (CKEditor output) —
     resolve straight to the entity by UUID, no URL parsing.
  2. `<drupal-media>` embeds (media_embed) — same attribute shape, resolved to
     the media's source file.
  3. Link-field URIs — `entity:file/N` and `entity:media/N` resolve directly;
     `internal:/…` and absolute URLs reduce to (4).
  4. Href parsing, last resort — `/sites/default/files/…` (public) and
     `/system/files/…` (private) reconstructed to `public://` / `private://`
     via the stream wrapper manager and looked up in `file_managed`.
  Parsing is `Html::load()` + `DOMXPath`, never regex.
- **`LinkedFileExtraction`** processor (`src/Plugin/search_api/processor/`):
  the Search API glue. Gated to Wayfinder-backend indexes, it declares one
  aggregate computed property `saw_linked` (the issue's "a separate field with a
  lower boost"), scans configured text and link fields on the item, hands their
  raw values to the discoverer, and indexes the extracted text — recording each
  file→item reference in the map on the way through.
- **`FileExtractionProcessorBase`** (`src/Plugin/search_api/processor/`):
  extracted the cache/queue/extract loop and the file→item map recording shared
  by attached-file (#262) and linked-file (#265) discovery, so the two
  processors stay thin and their extraction behaviour stays identical.
  `FileExtraction` was refactored to extend it; its #262 tests are unchanged
  and green.
- **`search_api_wayfinder.services.yml`**: wires the discoverer service
  (`@entity_type.manager`, `@stream_wrapper_manager`).

## Design decisions (hard to change later)

1. **A new processor, not a flag on `FileExtraction`.** Attached and linked
   extraction are independently toggleable, the discovery logic is substantial
   enough to warrant its own home, and the code boundary mirrors the issue
   boundary (#262 vs #265). The shared extraction plumbing is a base class, not
   duplication.
2. **One aggregate field, `saw_linked`, not one per source.** The issue's
   fan-out hard part is one document linked from many items: the content-hash
   cache (#263) extracts it once regardless, and a single lower-boost field
   keeps fifty copies of one PDF from dominating relevance. Per-source fields
   would be a refinement, not a need.
3. **Media resolved by inspecting referenced files, not `MediaInterface::getSource()`.**
   `referencedEntities()` filtered to `FileInterface` surfaces any media type's
   source file, needs no `media` module dependency, and needs no test-sandbox
   autoload shim (the media namespace is not mapped in `composer.json`, by
   design — module namespaces resolve at runtime via core's classloader on a
   real site only).
4. **Scan configured text and link fields, not the rendered node.** Raw field
   values are parsed with `Html::load()`; a full view mode would drag in menus,
   footers, and related-content teasers, so every node would index the same
   site-wide PDFs. Text field types scanned: `text`, `text_long`,
   `text_with_summary`; plain `string`/`string_long` are excluded (no markup).
5. **External links off by construction.** Only managed files resolve, so an
   external URL simply matches nothing — nothing is fetched, so there is no
   SSRF surface, no latency, no unbounded fetch size. The issue's "if enabled
   later" (domain allowlist + size/timeout caps) would mean *fetching* external
   documents, which is a deliberately different, larger feature.
6. **Depth capped at one hop.** A discovered file's own content is never parsed
   for further links; that is the natural behaviour of the design (we never
   treat an extracted document as HTML to scan).

## Reuse of #262 / #263

- **Content-hash cache** — a linked file shared by N items is extracted once
  (`LinkedFileExtractionTest::testAFannedOutLinkedFileIsExtractedOnceAndRecordedForEachItem`),
  the same way #263's attached-file path is.
- **File→item map** — `LinkedFileExtraction` records URL-discovered references
  with the same `FileReferenceMap::record()` attached files use; there is no
  entity-reference field to derive them from, which is exactly why #263 kept the
  map explicit.
- **Invalidation** — unchanged. `hook_file_update` / `_delete` →
  `ExtractionInvalidator` already reads the map generically; linked references
  flow through it for free.

## Mutation tests (guard code)

Per the repo rule that code whose whole value is *failing correctly* gets
mutation-tested, each load-bearing guard was broken deliberately, confirmed to
be caught, and reverted:

- **Dedup** (`$found[$id] = $file` → `$found[] = $file`): caught by
  `testFilesDiscoveredMultipleWaysAreDeduplicated`.
- **External/unmanaged href guard** (prefix-match skip dropped): caught by
  `testAnExternalAbsoluteHrefResolvesToNothing` (the storage's
  `loadByProperties` is asserted never to be called).
- **`saw_linked` gate** (early-return dropped): caught by
  `testAddFieldValuesDoesNoDiscoveryWhenSawLinkedIsNotOnTheItem` (the discoverer
  is asserted never to be called).
- **Non-document entity-type skip** (`data-entity-type="node"` routed to the
  file branch): caught by `testIgnoresANonDocumentDataEntityType` and
  `testALinkToANodeResolvesToNothing`.

The empty-extraction skip
(`testAddFieldValuesLeavesTheFieldEmptyWhenExtractionYieldsNothing`) and the
entity-not-loadable no-op
(`testAddFieldValuesNoOpsWhenTheOriginalObjectCannotBeLoaded`) are likewise
guarded by dedicated tests.

## Upstream note

The issue asked to read `search_api_attachments` issue #3510920's "file
aggregator" MR !40 before designing. This hermetic environment has no network,
so I worked from the issue's own summary of it rather than fetching the MR. The
two reviewer-feedback points the issue flags are honoured: the design supports
multiple active discovery sources (all four mechanisms feed one aggregate field
and one extract loop), and recursion is capped at one hop per the issue's
explicit "Depth" hard part rather than left unbounded.

## Out of scope / follow-ups

- **#266 (settings form / config schema)** will surface processor config; the
  linked processor adds no config of its own yet (no admin UI built here).
- **Applying #264's `ExtractFileValidator` indexability rules** to discovered
  linked files. Attached files are not yet run through it in the processor
  either (#262 did not wire it), so linked files stay consistent with that; a
  slice that wires the validator should do both at once.
- **Additional local stream schemes** (e.g. an S3 wrapper) beyond public and
  private. The two named in the issue ship; a third is one line in
  `LinkedFileDiscoverer::LOCAL_SCHEMES` once a site demonstrates it.
- **`<img src>` / other element hrefs** beyond `<a href>` and the
  `data-entity-type` attribute path. Images carry no extractable text and the
  attribute path already covers CKEditor-inserted files, so only `<a href>` is
  scanned for raw hrefs; a site that links documents from `<img>` is a
  documented edge case.
- **Integration coverage** is a manual follow-up (`tests/integration/run.sh`,
  `WAYFINDER_INTEGRATION=1`); the unit tests are the acceptance gate per the
  issue ("`vendor/bin/phpunit` green"), matching #262/#263's stance.
